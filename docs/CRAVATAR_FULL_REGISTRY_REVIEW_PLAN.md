## 1. 背景与事实基线

2026-08-05 对生产库进行只读查询时，`wp_9_avatar_verify` 包含：

| 来源 | 行数 |
|---|---:|
| `gravatar` | 3,068,649 |
| `cravatar` | 18,320 |
| 合计 | 3,086,969 |

当前 WordYeah 中的 1,100 条记录只来自 Cavalcade 历史任务抽样，再按
`image_md5` 关联头像登记表。现有导出器从 `wp_cavalcade_jobs` 起步，单页最多
5,000 条，并不遍历 `wp_9_avatar_verify` 全表。因此 1,100/1,100 仅表示该批
样本全部进入审核记录，不表示全库覆盖。

生产表的当前结构事实：

- `image_md5 varchar(100)`：主键；
- `user_id int`；
- `url varchar(255)`；
- `type varchar(255)`：当前关注 `cravatar|gravatar`；
- `hash_type enum(md5,sha256)`；
- `status int`；
- 没有 `created_at` / `updated_at`，不能依赖时间字段做可靠增量水位；
- 抽样行仍保存 `https://cravatar.cn/avatar/<hash>`，该域名只作历史元数据，
  实际采集必须改写为 `cravatar.com` 或 `cn.cravatar.com`，不得请求旧域名。

## 2. 目标与非目标

### 2.1 目标

1. 对快照范围内每一条 Cravatar/Gravatar 登记记录建立可追溯审查状态。
2. 审查当前实际返回的头像内容，而不是把历史 URL 或旧 `image_md5` 当作图片证据。
3. 先用本地专用模型完成全量快筛，只把疑似、异常和质量抽检样本送高级视觉模型。
4. G2A Web 号池承担高级视觉一审，本机 Ollama 承担失败兜底和独立二审。
5. 高置信度结论由 Agent 自动闭环；只有两轮 AI 后仍不确定的项目进入人工队列。
6. 全过程可暂停、恢复、重试、去重、审计，并能准确报告覆盖率和遗漏原因。
7. 首次全量完成后切换为增量审查，避免再次形成百万级积压。

### 2.2 非目标

- 本计划不直接更新 `wp_9_avatar_verify`、Cavalcade、用户头像或黑名单。
- 不恢复腾讯云或其他第三方内容审核 API。
- 不把 3,086,969 张图片全部提交给高级视觉模型。
- 不把政治人物、人脸或宗教符号本身判为违规；这些只能作为受控标签或人工关注信号。
- 生产记录、本地原图和生产表结构均保持不变。
- 不把登记表行数直接当成“唯一当前图片数”或“唯一用户数”。

## 3. 核心判断

### 3.1 登记行、URL 和当前图片不是同一个对象

首次全量必须保存三层身份：

1. **登记身份**：`registry:<image_md5>`，对应生产登记行；
2. **头像地址身份**：规范化后的 URL path hash；
3. **当前内容身份**：下载字节的 SHA-256。

同一当前图片可能被多个登记行引用；历史 `image_md5` 也可能与 CDN 当前返回字节不一致。
模型只对“当前内容身份”推理一次，再把结论扇出到所有关联登记行。任何缺少当前图片
证据的记录只能标记为 `fetch_missing`、`fetch_error` 或 `invalid_metadata`，不能自动通过。

### 3.2 首次全量不是 308 万次高级视觉调用

推荐路径：

```text
生产快照/分页导出
  → URL 规范化与合法性检查
  → CDN 受控采集
  → 当前内容 SHA-256 去重
  → 解码与文件安全检查
  → 本地多检测器快筛
      ├─ 高置信度安全 → 自动通过 + 质量抽检
      ├─ 高置信度违规 → 自动拒绝/黑名单候选 + 质量抽检
      ├─ 低置信度/模型分歧/特殊风险 → G2A AI 一审
      └─ 文件异常/证据缺失 → 留置
  → G2A 失败时 Ollama 兜底
  → 仍不确定时独立 Ollama 二审
  → 仍不确定 → 人工队列
```

### 3.3 来源不是免审条件

`avatar_origin=gravatar|cravatar` 仅表示来源。两类记录使用相同图片安全策略、路由规则、
质量抽检和人工升级条件。报告必须分别显示两类覆盖率，但不得给任一来源免审。

## 4. 方案选择

### 4.1 生产数据获取方式

#### 方案 A：从只读副本或数据库快照导出（推荐）

- 在只读副本、备份恢复实例或一次性快照上完成全表遍历；
- 使用 `image_md5` 主键做 keyset 分页；
- 不占用生产连接执行长时间扫描；
- 快照总数固定，容易做覆盖率和哈希验收。

缺点：需要现有备份/副本入口，准备时间较长。

#### 方案 B：生产库在线 keyset 分页

- `WHERE image_md5 > :cursor ORDER BY image_md5 LIMIT :page_size`；
- 每页 1,000–5,000 条，自适应限速；
- 不使用 `OFFSET`，不启用长事务；
- 每页落盘后更新本地 cursor。

缺点：表没有更新时间；扫描期间新插入且排序落在 cursor 之前的记录可能漏掉。因此必须
同时接住新增审核任务，并在首次扫描结束后做第二次差异核对。生产库负载异常时立即停止。

#### 方案 C：直接扩展生产表并增加审查字段

不采用。首次审查阶段修改 300 万行生产表、增加索引或扫描标记会放大锁、回滚和业务风险。
WordYeah 应保存自己的审核账本，写回动作另立计划审批。

### 4.2 首次审查存储

推荐继续使用 SQLite WAL，但把高吞吐阶段拆开：

- 不为 308 万条登记元数据逐条创建模型 job；先批量写入 `registry_assets` 暂存账本；
- 当前内容去重后，才按唯一内容创建快筛任务；
- 高级视觉任务仍使用现有持久 job/lease；
- 批量写入使用单写者和事务批次，避免大量 worker 争抢 SQLite 写锁；
- 达到 100 万、200 万、全量三个节点时分别执行完整性检查和备份。

若 100,000 条试运行显示 SQLite 持续写入低于 50 records/s、锁等待超过 5% 或数据库
恢复时间超过 10 分钟，再评估 PostgreSQL；不能在没有压测证据时提前迁移。

## 6. 分类与路由策略

### 6.1 文件安全门

任何模型执行前必须完成：

- 仅允许 JPEG、PNG、WebP、GIF、BMP；
- 限制下载字节、像素、宽高、帧数和解压比例；
- 拒绝 HTML、SVG、重定向到非 allowlist host、损坏图片及路径逃逸；
- 动图在头像 MVP 中不直接自动通过；首帧与多帧策略需单独验证；
- 获取失败不得映射为 `allow`。

### 6.2 本地快筛

Falconsai 只能覆盖 NSFW，不足以单独代表完整头像安全结论。首次全量至少规划：

1. NSFW/裸露检测；
2. 图片质量与解码异常；
3. OCR/二维码/明显广告信号；
4. 暴力、血腥、极端主义符号等模型能力评估；
5. 人脸、政治人物仅作标签，不自动判违规；
6. 模型分歧、特殊类别和低质量图片进入高级视觉。

在代表性标注集没有通过门槛前，快筛结果只能 shadow，不允许执行生产替换。

### 6.3 路由阈值

阈值不能凭经验固定，需通过标注集校准。初始设计：

- `auto_allow`：所有必需检测器均为低风险，文件证据完整，且不命中特殊类别；
- `auto_reject`：阻断类别达到高精度阈值；普通违规对应默认头像替换候选；明确恶意内容才是黑名单候选；
- `vision_review_1`：低置信度、模型分歧、OCR/符号/人物语义、动图、异常构图；
- `vision_review_2`：一审置信度不足、返回不完整、结论与快筛冲突；
- `human_required`：两轮仍不确定、政治人物争议、疑似未成年人、严重风险或模型证据不足；
- `held`：文件缺失、下载失败、模型不可用、数据不一致。

### 6.4 质量抽检

- 自动通过：随机抽检 0.2%–0.5%，并按来源、风险带、模型版本分层；
- 自动拒绝：至少抽检 1%，严重黑名单候选首次上线前抽检 100%；
- G2A 自动结论：抽检 0.5%；
- 模型版本、提示词或阈值变化后重新建立抽检批次；
- 抽检失败触发该风险带自动暂停，不只生成告警。

## 7. 并发与背压设计

### 7.1 采集

- 首次从 16 并发开始，经 10,000 条试运行后逐级测试 32、64、128；
- 以 host 为维度设置 token bucket，不直连源站；
- 429、5xx、超时使用指数退避和 jitter；
- 5 分钟窗口内 429+5xx 超过 2% 时降一档，超过 5% 时停止采集；
- 下载任务队列达到高水位时暂停生产数据导出，避免元数据无限堆积。

### 7.2 本地快筛

- 对 1、2、4、8、16 worker 做阶梯压测；
- 同时比较单图推理和 batch 8/16/32；
- 选择吞吐稳定且内存、温度、系统交互不受明显影响的配置；
- 目标是连续 6 小时无任务丢失、无 swap、无模型崩溃；瞬时速度作为辅助指标记录。

### 7.3 G2A Web

- 客户端只使用池化 `g2a_` 网关 key，不复制个人 Web 登录态；
- 并发从 16 开始，测试 32、64、128；
- 使用 AIMD：稳定窗口逐步加并发，429/超时立即减半；
- 按模型、错误类型、延迟和 fallback 分开计数；
- G2A 熔断后不得把全部任务瞬间压到 Ollama；任务保留并按本机容量缓慢回退；
- 不把 pool available 数量直接解释为可用并发，只有真实请求压测能决定并发上限。

### 7.4 Ollama

- `qwen3-vl:8b`：G2A 失败兜底；
- `gemma3:12b`：独立二审；
- 分别测试 1、2、4 并发，记录总吞吐而不是只看单请求延迟；
- 两个模型不得无界并行加载；设置内存和队列高水位；
- 本机模型不可用时任务留置，不再外部降级。

## 8. 分阶段执行计划

### Phase 0：语义与范围确认

任务：

1. 固化 `status`、`type`、`hash_type` 和 URL 字段的业务语义；
2. 核对登记行与用户、当前 CDN 头像、历史图片的对应关系；
3. 分组统计 type/status/hash_type/URL host/URL 合法性；
4. 明确“审查当前返回内容”作为首次全量目标；
5. 确定从只读副本还是生产 keyset 导出。

门槛：所有字段有书面定义；不能解释的状态进入留置，不得按安全处理。

### Phase 1：只读全量导出与本地账本设计

计划文件：

- 新增 `scripts/cravatar_registry_export.php`；
- 新增 `src/wy_cravatar/registry.py`；
- 扩展 `src/wy_cravatar/__main__.py`；
- 新增相应 migration、单元测试和部署说明；
- 保留 `scripts/cravatar_cavalcade_export.php` 作为任务队列导出器，不混用两种来源。

门槛：1,000 条模拟表和生产只读小样本均可暂停、恢复和幂等重跑；零生产写入。

### Phase 2：10,000 条分层 pilot

样本必须覆盖：

- Gravatar/Cravatar；
- 各 registry status/hash_type；
- 不同 URL 形态；
- 不同文件类型、尺寸和内容哈希重复组；
- 历史 MD5 与当前内容一致/不一致；
- 下载失败与非法图片。

输出：采集吞吐、CDN 错误率、内容去重率、快筛风险分布、G2A 命中率、Ollama fallback
比例、人工升级率、单位任务存储量。

门槛：连续运行 2 小时，零任务丢失；恢复测试后计数一致；无旧 `.cn` 出站请求。

### Phase 3：标注与阈值校准

1. 从 pilot 中建立分层人工标签集；
2. 自动通过样本至少抽取 3,000 条，用于估计低频漏审；
3. 自动拒绝和高风险样本做富集抽样；
4. 至少两名独立 reviewer 处理关键子集，分歧进入仲裁；
5. 固化模型版本、提示词版本、策略版本和阈值。

初始质量门槛：

- 自动拒绝精确率 ≥99.5%；
- 已标注违规集召回率 ≥99%；
- 自动通过抽检漏审率 ≤0.1%，并报告置信区间；
- 模型错误不得转为 allow；
- 特殊风险禁止普通批量决定。

样本不足以支持统计结论时必须报告 `INCOMPLETE`，不能降低门槛凑通过。

### Phase 4：100,000 条 soak

- 使用计划并发阶梯；
- 连续运行至少 6 小时；
- 注入 G2A 429、超时、无效 JSON、Ollama 停止、SQLite 重启和 CDN 失败；
- 验证 lease 回收、退避、熔断、fallback、暂停和恢复；
- 测量数据库体积、WAL、写锁、CPU/GPU、内存、温度和队列积压。

门槛：覆盖率 100%；重复任务 0；丢失任务 0；错误路径 allow 0；人工队列只包含最终不确定项。

### Phase 5：全量 shadow

1. 建立不可变 snapshot/batch；
2. 分区运行并持续发布水位；
3. 采集、快筛、AI 一审/二审并行流水；
4. 每 100,000 条生成 checkpoint；
5. 达到 1M、2M、全量时分别备份和核对；
6. 首轮结束后执行差异补扫，接入扫描期间新增头像；
7. 只生成拟执行动作，不写回生产。

完成门槛：

- `covered + invalid_metadata + fetch_missing + held = snapshot_expected`；
- 每个登记 source ID 恰有一个终态或明确留置原因；
- 当前内容相同的记录共享推理结果；
- Gravatar 与 Cravatar 分别报告覆盖率；
- 全部质量门槛通过；
- 未产生任何生产写入。

### Phase 6：结果复核与增量接管

- 复核风险分布、来源差异、status 差异和模型错误；
- 对自动通过、自动拒绝、黑名单候选完成抽检；
- 将新增头像入口接入 WordYeah，保证先审后展示或按现行策略 shadow；
- 形成生产写回提案、回滚策略和小流量 canary；
- 写回属于独立高风险任务，需另行批准。

## 9. 容量、时间和成本模型

- `Q`：质量抽检比例；
- `C`：G2A 有效并发；
- `L`：G2A 平均延迟；
- `B`：fallback 到 Ollama 的比例。

估算公式：

```text
快筛时间 ≈ U / F
高级视觉调用数 ≈ U × (P + Q)
G2A 时间 ≈ 调用数 × L / C
Ollama 调用数 ≈ 高级视觉调用数 × B + 二审数
```

### 9.2 当前仅供容量规划的范围

- 当前持久队列已验证约 50 jobs/s，308 万条约 17.1 小时；
- 图片样本平均约 6.6 KB，但全库分布未知；准备 50–100 GB 工作空间；
- 若高级视觉比例为 1%–5%，调用约 30,870–154,348 次；
- G2A 32 路、12.2 秒平均延迟时，纯理论约 3.3–16.3 小时；
- 429、超时和 fallback 会延长时间，不能用理论值作承诺；
- 采集、快筛和 AI 复审并行后，首次全量目标窗口为 1–4 天，最终承诺必须由
  100,000 条 soak 数据给出。

### 9.3 成本边界

- 腾讯云及第三方内容审核 API：0；
- G2A：不按单次 API 计费，但消耗自管 Web 号池容量和风控余量；
- Ollama：本机电力和设备占用；
- 存储：预计 50–100 GB 临时工作空间；
- 人工：取决于 `human_required` 与抽检量；pilot 必须测出真实比例后才能预算。

## 10. 监控与自动停止

必须提供以下指标：

- snapshot expected/exported/reconciled；
- fetch queued/running/succeeded/missing/invalid/retried；
- CDN p50/p95、429、4xx、5xx、吞吐；
- 唯一内容数与去重率；
- fast scan 各风险带和错误数；
- G2A 并发、p95、429、timeout、invalid response；
- Ollama p95、并发、fallback、模型错误；
- AI 一审/二审/人工升级数量；
- SQLite WAL、锁等待、队列深度、最老任务年龄；
- 每个来源的覆盖率和终态分布。

自动停止条件：

- 发现生产写操作；
- CDN 5 分钟错误率 >5%；
- 生产数据库查询 p95 >2 秒或宿主监控出现明显负载/复制延迟异常；
- SQLite 锁错误导致任务无法可靠落盘；
- 任一模型错误被路由为 allow；
- 任务计数无法守恒；
- G2A 熔断且 Ollama 队列超过高水位；
- 模型版本或策略版本在批次中途漂移。

## 12. 验收标准

1. 快照范围和来源计数有不可变证据；
2. Gravatar 与 Cravatar 均无免审分支；
3. 所有登记 source ID 有终态或明确留置原因；
4. 计数严格守恒，重复任务和丢失任务均为 0；
5. 模型错误、下载错误和证据缺失产生 allow 的数量为 0；
6. `.cn` 实际出站请求为 0；
7. 自动拒绝精确率、违规召回率和自动通过抽检达到 Phase 3 门槛；
8. 100,000 条 soak 连续 6 小时通过并完成故障演练；
9. 全量期间生产库和 CDN 未触发停止条件；
10. 无 WordPress、Cavalcade、登记表或头像状态写入；
11. G2A/Ollama 模型、提示词、策略版本可逐项追溯；
12. 完成扫描期间新增头像的差异补扫和增量接管。

## 13. 回退与数据保留

首次全量为 shadow，只读生产侧，因此回退动作是：停止导出和 worker、保留 cursor、关闭新任务、
核对正在运行 lease，等待或回收后生成中止报告。不得通过删除数据库或媒体目录“回退”。

本地数据保留策略在 pilot 后决定：

- 违规、争议、人工、质量样本和错误证据长期保留；
- 自动通过原图是否清理必须经过单独确认；
- 即使清理原图，也保留 source mapping、内容哈希、模型版本和审计事件；
- 删除任何批次或媒体前必须生成 itemized 清单并取得确认。

## 14. 前置决策门

正式实施前必须确认：

1. 使用只读副本/快照，还是允许生产库限速 keyset 扫描；
2. 生产数据库和 CDN 的可接受负载窗口；
3. `status` 字段的业务含义；
4. 首次审查覆盖的违规类别及处置映射；
5. 自动通过、自动拒绝、黑名单的质量门槛；
6. 原图和审核证据保留周期；
7. 全量 shadow 完成后是否进入生产写回评审。

未通过这些决策门，只能进行离线开发、模拟测试和小样本只读 canary，不能启动全量。

## 15. 风险预演

### 风险一：审错对象

登记表保存的是历史 MD5，但 CDN 当前头像已经变化，最终结论无法对应用户看到的内容。

缓解：分离 registry identity、URL identity 和 current content identity；记录采集时间与内容 SHA；
写回前重新确认当前内容未变化。

### 风险二：并发压垮 CDN、数据库或号池

缓解：副本优先、keyset、token bucket、AIMD、分阶段放量、自动停止；pool available 不作为并发证据。

### 风险三：NSFW 模型把其他违规内容自动通过

缓解：不把 Falconsai 当完整安全模型；补充检测器、VLM 路由、分层抽检和 fail-closed。

### 风险四：G2A 熔断导致 Ollama 雪崩

缓解：fallback 独立高水位、有限并发、任务留置；禁止瞬时全量转移。

### 风险五：全量完成时仍漏掉扫描期间新增记录

缓解：全量期间接住新增审核任务；完成后差异补扫；没有可靠增量证据不得宣布 100% 覆盖。

## 16. 决策记录

- **决定**：采用“全量本地快筛、内容去重、疑似项高级视觉、最终例外人工”的分层方案。
- **驱动因素**：308 万规模、G2A 号池稳定性、人工最少介入、不能恢复外部审核 API。
- **未选方案**：全量高级视觉；成本和号池风险无必要。直接生产表加字段；首次阶段写入风险过高。
- **后果**：必须先完成快照语义、内容身份和阈值校准；首次准备工作比直接跑模型多，但结果可追溯、可恢复。
- **后续**：Phase 0 决策门通过后再拆分实施任务；本文件本身不构成执行授权。
